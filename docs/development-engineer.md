# Development Engineer

The Race Chief owns a persistent engineering backlog, chooses bounded jobs and
reviews completed work. Each job has an isolated workspace, an edit allowlist,
acceptance checks and retained evidence. The private Windows deployment combines
a recurring Codex Chief check-in with a Pi Durable specialist and a local job host.
The specialist's identity and work survive individual process lifetimes.

The Chief reviews pending outputs before dispatching further work. Successful
execution enters awaiting review. Acceptance checks the actual changes, tests,
complete workspace inventory and exact artifact bytes. Interrupted attempts are
reconciled against their original process and artifact receipts before any retry.
Rejected and insufficient outputs stay available for diagnosis.

Standing maintenance permission represents the user's authorization for work
between drives. It records the original grant and can be revoked. Physical seat
presence remains a separate fact. Each operation additionally needs a fresh,
bounded permit and current evidence that the simulator and live visits are idle.
New arrivals, simulator activity, unknown state, expired observations and process
ambiguity prevent dispatch. The host continues observing during a job and requests
interruption when its permission becomes invalid.

The Chief must inhibit engineering as soon as the driver reports returning,
before preparing the rig. The native observer cannot read chat messages and
only watches configured visit roots plus simulator processes. Additional visit
roots must be configured before use.

The selected runtime is frozen and hashed. Future source changes use a new runtime
version so ordinary development cannot invalidate evidence from older jobs. The
current implementation uses an ORC-specific subset of Standard Agent
Specification concepts for specialist ownership, identity and lifecycle. Its Pi
adapter and local maintenance rules have their own contracts. Full SAS
conformance, automatic logon recovery and power-loss durability remain unverified.

The Chief's recurring check-in supplies wake-up and review. The local runtime
uses the installed Codex connection and checks ChatGPT authentication before an
inference request. It retains provider failures and refuses unapproved fallback
access. Local recorder, fuel and radio services retain independent ownership.
Live simulator impact and acoustic delivery require separate evidence.

The initial local deployment completed one real isolated engineering job through
the installed Codex connection. The Chief reviewed its exact changes and
independently passed twelve contract tests before adopting the helper. Persistent
identity was verified across fresh processes. The first hourly scheduled wake
ran and passed native idle admission, but its worker failed before inference
because the provider could not open its local state database under the launch
sandbox. The failure and unchanged workspace were preserved. Automated
between-drive work then received a reviewed recovery repair. It explicitly
closes this narrow initialization-only failure while preserving its original
receipt, and the closure survives a fresh process. Native provider initialization
passed through the normal approval mechanism. A subsequent scheduled diagnostic
job reached its time limit, retained its partial work, then resumed the same
thread on the next check-in and completed. The Chief independently passed 23
focused tests and accepted its private diagnostic artifacts. This establishes
bounded interruption, continuation and review for that job; reboot recovery and
live fuel acceptance remain separate unverified gates.

Later offline work diagnosed a race between independently published fuel evidence
and developed a private service-owned decision candidate with durable request
records and native prerequisite checks. Its current regression and lint checks
pass, but the bounded job remains unfinished. Normal approved-visit integration,
armed service-loop handoff and an independently advancing source still need
verification. No candidate has been activated on the rig or cleared for driving.

Review also found that the current runtime stores Chief operation notes for
admission without including those notes in a resumed model turn. Resumption
repeats the original task. Persisted notes therefore do not establish that the
worker received corrective feedback. A separate runtime repair is planned to
bind and retain the exact feedback submitted on each operation; the selected
runtime and older job evidence remain unchanged pending review.
